# Feature Mode

Реализуй новую фичу системно: сначала понять → спросить → спроектировать → реализовать → проревьюить.

**Стек:** Vue 3 + TypeScript strict + Pinia + Vue Router + Tailwind CSS v4 + FSD v2.1.
**Язык ответов:** русский. Код, пути, имена — английский.

Запрос: $ARGUMENTS

---

## Фаза 1: Discovery

**Цель:** понять что нужно построить.

1. Создай todo-список со всеми фазами.
2. Если запрос расплывчатый — спроси:
   - Какую проблему решает фича?
   - Кто пользователь и что он делает?
   - Есть ли ограничения (дедлайн, scope, совместимость)?
3. Напиши user story: **"Как `<роль>`, я хочу `<действие>`, чтобы `<outcome>`"**
4. Перечисли 3-5 acceptance criteria.
5. Зафиксируй edge cases: пустое состояние, ошибка, загрузка, нет прав.
6. Подтверди понимание с пользователем.

---

## Фаза 2: Исследование кодовой базы

**Цель:** понять существующие паттерны до начала проектирования.

Запусти 2-3 агента **code-explorer параллельно**, каждый с разным фокусом:

- **Агент 1:** "Найди фичи похожие на `[фича]`, проследи их реализацию через FSD-слои от page до api"
- **Агент 2:** "Какие entities, stores, composables уже существуют для `[область]`? Что можно переиспользовать?"
- **Агент 3:** "Покажи UI-паттерны для `[область]` — как организованы widgets, какие компоненты из shared/ui уже есть"

После завершения агентов — прочитай все ключевые файлы, которые они вернули (5-10 штук). Построй детальное понимание.

Представь итог: что уже есть, что переиспользовать, какие паттерны применить.

---

## Фаза 3: Уточняющие вопросы

**Цель:** закрыть все неоднозначности до проектирования.

**КРИТИЧЕСКИ ВАЖНО: не пропускать эту фазу.**

1. Изучи находки из исследования + оригинальный запрос.
2. Найди неоднозначности: edge cases, обработка ошибок, интеграции, scope, UX-детали, права доступа.
3. **Задай все вопросы пользователю одним списком.**
4. **Жди ответов перед тем как проектировать.**

Если пользователь говорит "на твоё усмотрение" — дай рекомендацию и получи явное подтверждение.

## Фаза 4: UI/UX Design

**Цель:** описать все состояния и поведение интерфейса.

Опиши:
- **UI-состояния:** default / loading / error / empty / success
- **Responsive:** 375px (mobile) / 768px (tablet) / 1280px (desktop)
- **Интерактивные состояния:** `:hover`, `:focus-visible`, `:disabled`
- **Компоновка:** какие widgets/features/компоненты задействованы

---

## Фаза 5: Архитектурный дизайн

**Цель:** спроектировать реализацию с учётом FSD.

Запусти **2 агента code-architect параллельно** с разными подходами:

- **Агент 1:** "Minimal — максимальное переиспользование существующего кода, минимум новых файлов"
- **Агент 2:** "Clean — правильная FSD-структура, чистое разделение слоёв, масштабируемость"

После получения результатов:
1. Сформируй своё мнение — какой подход лучше для этой задачи.
2. Представь пользователю: краткое сравнение, trade-offs, **рекомендацию с обоснованием**.
3. **Спроси пользователя какой подход выбрать.**

Формат для выбранного подхода:
```
Slice: features/dish-filter
Layer: features
Depends on: entities/dish (IDish), entities/category (ICategory)
Public API (index.ts): <DishFilterPanel />, useDishFilter()

features/dish-filter/
├── ui/DishFilterPanel.vue
├── model/
│   ├── types.ts
│   ├── filterRules.ts
│   └── useDishFilter.ts
└── index.ts
```

## Фаза 6: Реализация

**Цель:** реализовать фичу по выбранной архитектуре.

**НЕ НАЧИНАТЬ БЕЗ ЯВНОГО ПОДТВЕРЖДЕНИЯ ПОЛЬЗОВАТЕЛЯ.**

1. Дождись подтверждения.
2. Прочитай все релевантные файлы из предыдущих фаз.
3. Реализуй по порядку: `shared` → `entities` → `features` → `widgets` → `pages` → `router`
4. Каждый файл — полный код с путём на первой строке, без `// ... rest of code`.
5. TypeScript interfaces — в отдельном блоке `model/types.ts`, не в компонентах.
6. Обновляй todo по ходу реализации.

**Правила реализации:**
- `<script setup lang="ts">` — без исключений
- Props через `defineProps<T>()`, emits через `defineEmits<T>()`
- HTTP только через `shared/api/http.ts` и `*/api/*.ts`
- Бизнес-правила → `model/domainName.ts`, логика → `model/useXxx.ts`, шаблон → `ui/*.vue`
- Page composable возвращает `reactive({})` для v-model совместимости
- Новые сущности регистрировать в `index.ts` slice

## Фаза 7: Code Review

**Цель:** убедиться что код корректен, прост и соответствует проекту.

Запусти **3 агента code-reviewer параллельно** с разными фокусами:

- **Агент 1:** "Проверь простоту и DRY — нет ли дублирования, лишних абстракций, можно ли упростить"
- **Агент 2:** "Проверь баги и корректность — edge cases, реактивность, типы, обработка ошибок"
- **Агент 3:** "Проверь FSD-соответствие — импорты, слои, три уровня (domain/logic/ui), public API"

После получения результатов:
1. Собери находки, выдели самые критичные (🔴 Blocker).
2. **Представь пользователю и спроси: исправить сейчас, отложить или оставить.**
3. Исправь по решению пользователя.
