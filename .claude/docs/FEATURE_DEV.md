# Feature Development Workflow

Системный 8-фазовый процесс разработки фич: понять → спросить → спроектировать → реализовать → проревьюить.

**Запуск:** `/feature <название или описание>`

---

## Зачем это нужно

Прямой путь "услышал → закодил" приводит к:
- Неправильно выбранному FSD-слою
- Дублированию существующих stores/composables
- Пропущенным edge cases (loading/error/empty)
- Архитектурным долгам, которые сложно рефакторить

Workflow встраивает правильные практики в процесс: исследование кодовой базы, вопросы перед дизайном, параллельные агенты для анализа.

---

## 8 фаз

### Фаза 1 — Discovery
Уточняет запрос, пишет user story, перечисляет acceptance criteria и edge cases. Подтверждает понимание с разработчиком.

### Фаза 2 — Исследование кодовой базы
Запускает 2-3 агента `code-explorer` параллельно с разными фокусами:
- Похожие фичи в проекте (что уже реализовано, какой паттерн)
- Существующие entities/stores/composables для переиспользования
- UI-паттерны: какие widgets/компоненты из `shared/ui` уже есть

Читает все ключевые файлы (5-10 штук) и представляет итог: что переиспользовать, какие паттерны применить.

### Фаза 3 — Уточняющие вопросы ⚠️
**Не пропускать.** Задаёт все неоднозначные вопросы одним списком перед проектированием. Ждёт ответов.

Типичные вопросы:
- Нужна ли пагинация / бесконечная прокрутка?
- Как обрабатывать отсутствие данных (empty state)?
- Есть ли роли/права доступа?
- Нужен ли optimistic update?

### Фаза 4 — UI/UX Design
Описывает все UI-состояния (default / loading / error / empty / success), responsive breakpoints (375px / 768px / 1280px) и компоновку (какие widgets/features задействованы).

### Фаза 5 — Архитектурный дизайн
Запускает 2 агента `code-architect` параллельно:
- **Minimal** — максимальное переиспользование, минимум новых файлов
- **Clean** — правильная FSD-структура, чистое разделение, масштабируемость

Представляет сравнение с trade-offs и рекомендацию. Ждёт выбора разработчика.

Пример вывода:
```
Slice: features/order-tracking
Layer: features
Depends on: entities/order (IOrder), shared/api/http.ts
Public API: <OrderTracker />, useOrderTracking()

features/order-tracking/
├── ui/OrderTracker.vue
├── model/
│   ├── types.ts
│   ├── orderTrackingRules.ts   ← чистые функции
│   └── useOrderTracking.ts     ← composable
└── index.ts
```

### Фаза 6 — Реализация
**Не начинает без явного подтверждения.** Реализует по порядку:
`shared` → `entities` → `features` → `widgets` → `pages` → `router`

Каждый файл — полный код. Соблюдает три слоя: `domain.ts` / `useXxx.ts` / `Component.vue`.

### Фаза 7 — Code Review
Запускает 3 агента `code-reviewer` параллельно:
- Простота и DRY (нет ли дублирования, лишних абстракций)
- Баги и корректность (edge cases, реактивность, типы)
- FSD-соответствие (импорты, слои, public API)

Представляет находки и спрашивает: исправить сейчас / отложить / оставить.

### Фаза 8 — Summary
Фиксирует что построено, ключевые решения, изменённые файлы, следующие шаги.

---

## Агенты

| Агент | Роль | Когда |
|---|---|---|
| `code-explorer` | Трассировка существующих фич, поиск паттернов | Фаза 2, ручной запрос |
| `code-architect` | Дизайн архитектуры, file tree, data flow | Фаза 5, ручной запрос |
| `code-reviewer` | Ревью кода, confidence ≥ 80 | Фаза 7, ручной запрос |

---

## Когда использовать

**Использовать `/feature` для:**
- Новых фич, затрагивающих несколько FSD-слоёв
- Фич с неясными требованиями или архитектурными вопросами
- Всего что потребует > 3 новых файлов

**Не использовать для:**
- Однострочных багфиксов → `/debug`
- Рефакторинга → `/refactor`
- Простых изменений с очевидной реализацией

---

## Быстрые подсказки

- **Конкретный запрос = меньше уточняющих вопросов.** "Добавь фильтрацию блюд по тегам в меню" лучше чем "добавь фильтры"
- **Фаза 3 критична** — пропущенный вопрос = переделка после реализации
- **Доверяй рекомендации архитектора** — она основана на анализе реального кода проекта
- **Не пропускай фазы** — каждая строится на предыдущей
